## Ключові промпти

Це **відредаговані, відтворювані формулювання**, а не дослівний лог: після роботи я підправив їх так, щоб кожен промпт давав потрібний результат з першого разу і закривав помилки, описані нижче. Для кожного — чому він працює. Рядки «❌ Слабка версія» — це реконструкція типових коротких формулювань, які приводять до відповідної помилки (причина кожної описана нижче); це ілюстрація, а не цитати.

1. **Правила й каркас** (спершу `CLAUDE.md`, потім каркас)
   > Ось тестове завдання, і в CLAUDE.md мої правила — прочитай обоє. Зроби каркас: Playwright + TypeScript strict, два проєкти ui і api, Page Object для saucedemo, BookingClient для restful-booker, GitHub Actions на push, щоб HTML-звіт ліз в артефакти. Доку пиши українською. Крім @playwright/test нічого не тягни.
   > _Чому працює:_ правила (локатори, без sleep/serial, баг не маскувати) задані в файлі один раз і діють на всі подальші промпти; заборона зайвих залежностей не дає агентові тягнути бібліотеки.

2. **UI-тести з перевіркою на реальному сайті**
   > Тепер UI: логін, каталог, 4 сортування, кошик, чекаут + негативні (кривий логін, захід без логіну, валідація форми чекауту). Локатори тільки getByTestId або getByRole. Ціни й суми не хардкодь, бери зі сторінки. І поки не запустиш npx playwright test — не кажи "готово"; якщо щось падає, покажи причину з trace. Селектори не вигадуй: не бачив DOM — так і напиши.
   > ❌ _Слабка версія, що веде до помилок №1 і №4:_ «Напиши UI-тести для saucedemo: логін, каталог, сортування, кошик, чекаут, 5–7 позитивних і 2–3 негативних». Без вимоги запускати й без «не вигадуй селектори» агент пише `data-test` з памʼяті, а хелпери на кшталт `slug()` ніхто не звіряє з усіма товарами.
   > _Чому працює:_ вимога запустити і показати причину падіння закриває помилку №1 (селектори «з памʼяті»); «скажи прямо» змушує агента відрізняти знане від припущеного.

3. **API-флоу**
   > Для API зроби флоу auth → create → update (і PUT, і PATCH) → delete → GET має дати 404. Одним тестом з test.step, без describe.serial. Після create і update звіряй дані через GET, а не по тілу відповіді. Усі запити тільки через BookingClient. І по кожному кроку напиши, який статус чекаєш і чому.
   > ❌ _Слабка версія, що веде до помилки №3:_ «Зроби API-флоу auth → create → update → delete → перевірка, щоб усе було зелене». Прагнення до зеленого прогону підштовхує агента фіксувати фактичну поведінку (`toBe(201)` для DELETE) замість правильного очікування.
   > _Чому працює:_ один тест із кроками дає незалежність від порядку і паралельність; перевірка через GET ловить «ехо» у відповіді; вимога пояснити очікуваний статус відкриває місця, де агент підганяє тест під факт.

4. **Баги без маскування**
   > Якщо сайт або API ведуть себе не за специфікацією — не підганяй очікування під те, що є. Лиши правильне очікування, постав test.fail(true, 'BUG-XXX: ...') і додай баг-репорт у README: кроки, очікуваний і фактичний результат. Потім зніми test.fail у тимчасовій копії й покажи, що тест падає саме на цій перевірці, а не через щось інше.
   > ❌ _Слабка версія, що веде до помилки №2:_ «Для відомих багів познач тести через test.fail, щоб CI був зелений». Агент ставить маркер і зупиняється: тест «очікувано падає» з будь-якої причини, хоч через 503 чи зламаний локатор.
   > _Чому працює:_ перевірка «падає з правильної причини» закриває помилку №2 (`test.fail` ховає будь-яке падіння); заборона підганяти очікування закриває №3 (DELETE → 201 у CRUD-флоу).

5. **Ревʼю як скептик**
   > Тепер глянь на все як скептичний ревʼюер, по кожному тесту: де він пройде, навіть якщо фіча зламана? Чи кожен баг з README має свій тест? Чи немає очікувань, підігнаних під фактичну поведінку? По кожній знахідці — файл, рядок і як саме це зламається.
   > ❌ _Слабка версія:_ «Перевір, що все гаразд» — агент відповідає «так, усе зелене» і не помічає, що для BUG-API-02 тесту взагалі немає, а DELETE замаскований у флоу.
   > _Чому працює:_ конкретні питання дають перелік замість загального «виглядає добре»; питання (б) знайшло відсутній тест на BUG-API-02.

6. **Генерація тесту з кейсу**
   > Візьми кейс testcases/TC-UI-NNN-*.md і зроби з нього тест за скілом testcase-to-playwright. Спочатку подивись Page Object і юзай що є; якщо методу бракує — додай його в Page Object, а не сирий локатор у тест. Поклади в tests/ui/generated/, запусти. В кінці коротко: що згенерував, пройшов чи ні, які ще файли чіпав.
   > ❌ _Слабка версія, що веде до помилки №5:_ «Згенеруй тест із кейсу й закоміть, якщо зелений». Зелений тест не гарантує чистого diff: дрібні дефекти в Page Object (як `this.error =page...`) проходять непоміченими.

## Де агент помилився і як я це помітив

1. **Локатори написані без доступу до сайту.** Пісочниця агента не мала мережевого доступу до saucedemo.com і restful-booker, тому всі `data-test`-селектори й тексти помилок агент написав «з памʼяті» і жоден тест локально не запускав — лише `tsc`. Помітив: агент сам про це сказав; перевірка — перший прогін у CI.
   _Що впало / що виправив:_ перший прогін `npx playwright test` — 23/23 зелені, жоден селектор чи текст помилки правити не довелося. Тобто цей ризик не матеріалізувався; головне, що він був неперевірений до запуску.

2. **`test.fail()` ховає будь-яке падіння, не лише баг.** У тестах BUG-* агент використав `test.fail(true, ...)`: якщо сервер віддасть 503 або локатор зламається, тест теж буде «очікувано падаючим» і зелений. Помітив на ревʼю.
   _Рішення:_ вручну відтворив BUG-UI-01 (прибравши `test.fail`: падає саме на `not.toHaveURL(/checkout-step-two/)`, URL = checkout-step-two.html), а BUG-API-01/02/03 перевірив через `curl` (200 / 201 / 500). Сам маркер не посилював — ризик лишається.

3. **Баг замаскований в CRUD-тесті.** У кроці «видалення» агент написав `expect(res.status()).toBe(201)` з коментарем «фіксуємо фактичну поведінку» — це пряме порушення правила з `CLAUDE.md` (баг не маскувати). Окремого тесту на BUG-API-02 не було взагалі. Помітив під час перевірки, що кожен із 4 багів має свій `test.fail`-тест: для BUG-API-02 його не знайшлося.
   _Що виправив:_ у флоу залишено `res.ok()`, додано окремий `BUG-API-02` з `test.fail` і очікуванням 200/204; README оновлено.

4. **`InventoryPage.slug()` ламається на одному з 6 товарів.** Агент виводив `data-test` кнопки з назви товару заміною всіх не-буквено-цифрових символів на `-`. Для «Test.allTheThings() T-Shirt (Red)» реальний атрибут — `add-to-cart-test.allthethings()-t-shirt-(red)` (крапка й дужки лишаються), тож метод давав неіснуючий селектор. 14 перших тестів цей товар не торкались, тому помилка сиділа непомітно. Помітив, коли конвеєр-генератор (`claude -p`) для TC-UI-001 («додати всі товари») звернувся до цього товару: агент у своєму звіті вказав на дефект `slug()`.
   _Що виправив:_ підтвердив реальні `data-test` скриптом-пробою на живій сторінці, `slug()` тепер міняє лише пробіли на `-`. Додатково зʼясував: агент-генератор обійшов проблему окремим методом `addAllToCart()` через `getByRole`, а сам `slug()` не чіпав — виправлення моє.

5. **Дрібна помилка форматування в згенерованому коді.** Агент-генератор (TC-UI-002) вніс у `CheckoutPage` рядок `this.error =page.getByTestId('error')` без пробілу. На роботу це не впливає, помітив у `git diff` після прогону. Виправив вручну; висновок — diff після кожної генерації треба читати, а не покладатись лише на зелений тест.
