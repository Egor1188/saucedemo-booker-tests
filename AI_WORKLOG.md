## Ключові промпти

1. **Старт / каркас**
   > Ось тестове завдання (вставлено текст). Збери репозиторій: Playwright + TypeScript, два проєкти `ui` і `api`, Page Object для saucedemo, клієнт для restful-booker, GitHub Actions зі звітом як артефакт. Документацію пиши українською.

2. **UI-тести**
   > 5–7 позитивних тестів на логін, каталог, сортування, кошик, чекаут і 2–3 негативні. Локатори тільки через data-test. Ціни в чекауті не хардкодь — бери з каталогу і перевір, що subtotal = сума, total = subtotal + tax.

3. **API-флоу**
   > Флоу auth → create → update → delete → get=404 одним тестом з test.step, щоб тести можна було паралелити. Після create і update перевір дані через GET, а не лише тіло відповіді.

4. **Баги**
   > Якщо API/сайт поводиться не за специфікацією — не підганяй тест. Залиш правильне очікування, познач `test.fail` з ID бага, баг-репорт — у README.

5. **Ревʼю**
   > Пройдися по тестах як ревʼюер: де тест може пройти, хоча функціональність зламана?

## Де агент помилився і як я це помітив

1. **Локатори написані без доступу до сайту.** Пісочниця агента не мала мережевого доступу до saucedemo.com і restful-booker, тому всі `data-test`-селектори й тексти помилок агент написав «з памʼяті» і жоден тест локально не запускав — лише `tsc`. Помітив: агент сам про це сказав; перевірка — перший прогін у CI.
   _Що впало / що виправив:_ перший прогін `npx playwright test` — 23/23 зелені, жоден селектор чи текст помилки правити не довелося. Тобто цей ризик не матеріалізувався; головне, що він був неперевірений до запуску.

2. **`test.fail()` ховає будь-яке падіння, не лише баг.** У тестах BUG-* агент використав `test.fail(true, ...)`: якщо сервер віддасть 503 або локатор зламається, тест теж буде «очікувано падаючим» і зелений. Помітив на ревʼю.
   _Рішення:_ вручну відтворив BUG-UI-01 (прибравши `test.fail`: падає саме на `not.toHaveURL(/checkout-step-two/)`, URL = checkout-step-two.html), а BUG-API-01/02/03 перевірив через `curl` (200 / 201 / 500). Сам маркер не посилював — ризик лишається.

3. **Баг замаскований в CRUD-тесті.** У кроці «видалення» агент написав `expect(res.status()).toBe(201)` з коментарем «фіксуємо фактичну поведінку» — це пряме порушення правила з `CLAUDE.md` (баг не маскувати). Окремого тесту на BUG-API-02 не було взагалі. Помітив під час перевірки, що кожен із 4 багів має свій `test.fail`-тест: для BUG-API-02 його не знайшлося.
   _Що виправив:_ у флоу залишено `res.ok()`, додано окремий `BUG-API-02` з `test.fail` і очікуванням 200/204; README оновлено.

4. **`InventoryPage.slug()` ламається на одному з 6 товарів.** Агент виводив `data-test` кнопки з назви товару заміною всіх не-буквено-цифрових символів на `-`. Для «Test.allTheThings() T-Shirt (Red)» реальний атрибут — `add-to-cart-test.allthethings()-t-shirt-(red)` (крапка й дужки лишаються), тож метод давав неіснуючий селектор. 14 перших тестів цей товар не торкались, тому помилка сиділа непомітно. Помітив, коли конвеєр-генератор (`claude -p`) для TC-UI-003 («додати всі товари») звернувся до цього товару: агент у своєму звіті вказав на дефект `slug()`.
   _Що виправив:_ підтвердив реальні `data-test` скриптом-пробою на живій сторінці, `slug()` тепер міняє лише пробіли на `-`. Додатково зʼясував: агент-генератор обійшов проблему окремим методом `addAllToCart()` через `getByRole`, а сам `slug()` не чіпав — виправлення моє.

5. **Дрібна помилка форматування в згенерованому коді.** Агент-генератор (TC-UI-004) вніс у `CheckoutPage` рядок `this.error =page.getByTestId('error')` без пробілу. На роботу це не впливає, помітив у `git diff` після прогону. Виправив вручну; висновок — diff після кожної генерації треба читати, а не покладатись лише на зелений тест.
