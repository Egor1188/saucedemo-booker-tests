## Ключові промпти

Це **відредаговані, відтворювані формулювання**, а не дослівний лог: після роботи я підправив їх так, щоб кожен промпт давав потрібний результат з першого разу і закривав помилки, описані нижче. Для кожного — чому він працює.

1. **Правила й каркас** (спершу `CLAUDE.md`, потім каркас)
   > Прочитай завдання і `CLAUDE.md`. Збери каркас: Playwright + TypeScript strict, проєкти `ui` і `api`, Page Object для saucedemo, `BookingClient` для restful-booker, GitHub Actions на push із HTML-звітом як артефактом. Документація українською. Нічого, крім `@playwright/test`, не додавай.
   > _Чому працює:_ правила (локатори, без sleep/serial, баг не маскувати) задані в файлі один раз і діють на всі подальші промпти; заборона зайвих залежностей не дає агентові тягнути бібліотеки.

2. **UI-тести з перевіркою на реальному сайті**
   > Напиши UI-тести: логін, каталог, 4 сортування, кошик, чекаут і негативні (невалідний логін, доступ без логіну, валідація форми). Локатори тільки `getByTestId`/`getByRole`. Очікувані значення (ціни, суми) бери зі сторінки, не хардкодь. Перш ніж казати «готово» — запусти `npx playwright test` і для кожного падіння покажи причину з trace. Не вигадуй селектори: якщо не бачив DOM, скажи прямо.
   > _Чому працює:_ вимога запустити і показати причину падіння закриває помилку №1 (селектори «з памʼяті»); «скажи прямо» змушує агента відрізняти знане від припущеного.

3. **API-флоу**
   > Флоу auth → create → update (PUT і PATCH) → delete → GET=404 одним тестом із `test.step`, без `describe.serial`. Після create і update перевіряй збережені дані через GET, а не лише тіло відповіді. Усі HTTP-виклики — тільки через `BookingClient`. Для кожного кроку впиши, який статус і чому очікуєш.
   > _Чому працює:_ один тест із кроками дає незалежність від порядку і паралельність; перевірка через GET ловить «ехо» у відповіді; вимога пояснити очікуваний статус відкриває місця, де агент підганяє тест під факт.

4. **Баги без маскування**
   > Якщо сайт чи API поводиться не за специфікацією — не змінюй очікування під факт. Залиш правильне очікування, познач `test.fail(true, 'BUG-XXX: ...')`, додай баг-репорт у README (кроки, очікуваний, фактичний результат). Після цього зніми `test.fail` у тимчасовій копії й покажи, що тест падає саме на очікуваній перевірці, а не з іншої причини.
   > _Чому працює:_ перевірка «падає з правильної причини» закриває помилку №2 (`test.fail` ховає будь-яке падіння); заборона підганяти очікування закриває №3 (DELETE → 201 у CRUD-флоу).

5. **Ревʼю як скептик**
   > Пройдися по кожному тесту: (а) де він пройде, хоча функціональність зламана? (б) чи кожен баг із README має свій тест? (в) чи є в тестах очікування, підігнане під фактичну поведінку? Для кожної знахідки — файл, рядок, сценарій відмови.
   > _Чому працює:_ конкретні питання дають перелік замість загального «виглядає добре»; питання (б) знайшло відсутній тест на BUG-API-02.

6. **Генерація тесту з кейсу**
   > Виконай алгоритм зі скіла `testcase-to-playwright` для `testcases/TC-UI-NNN-*.md`: прочитай Page Object, використай наявні методи, при потребі додай метод у Page Object, а не сирий локатор у тест; запиши в `tests/ui/generated/`, запусти тест. У кінці: що згенеровано, пройшов чи ні, які файли змінено.
   > _Чому працює:_ чіткий вхід, місце виходу і формат звіту; саме так агент сам помітив дефект `slug()` (помилка №4). Після генерації все одно потрібен `git diff` — див. помилку №5.

## Де агент помилився і як я це помітив

1. **Локатори написані без доступу до сайту.** Пісочниця агента не мала мережевого доступу до saucedemo.com і restful-booker, тому всі `data-test`-селектори й тексти помилок агент написав «з памʼяті» і жоден тест локально не запускав — лише `tsc`. Помітив: агент сам про це сказав; перевірка — перший прогін у CI.
   _Що впало / що виправив:_ перший прогін `npx playwright test` — 23/23 зелені, жоден селектор чи текст помилки правити не довелося. Тобто цей ризик не матеріалізувався; головне, що він був неперевірений до запуску.

2. **`test.fail()` ховає будь-яке падіння, не лише баг.** У тестах BUG-* агент використав `test.fail(true, ...)`: якщо сервер віддасть 503 або локатор зламається, тест теж буде «очікувано падаючим» і зелений. Помітив на ревʼю.
   _Рішення:_ вручну відтворив BUG-UI-01 (прибравши `test.fail`: падає саме на `not.toHaveURL(/checkout-step-two/)`, URL = checkout-step-two.html), а BUG-API-01/02/03 перевірив через `curl` (200 / 201 / 500). Сам маркер не посилював — ризик лишається.

3. **Баг замаскований в CRUD-тесті.** У кроці «видалення» агент написав `expect(res.status()).toBe(201)` з коментарем «фіксуємо фактичну поведінку» — це пряме порушення правила з `CLAUDE.md` (баг не маскувати). Окремого тесту на BUG-API-02 не було взагалі. Помітив під час перевірки, що кожен із 4 багів має свій `test.fail`-тест: для BUG-API-02 його не знайшлося.
   _Що виправив:_ у флоу залишено `res.ok()`, додано окремий `BUG-API-02` з `test.fail` і очікуванням 200/204; README оновлено.

4. **`InventoryPage.slug()` ламається на одному з 6 товарів.** Агент виводив `data-test` кнопки з назви товару заміною всіх не-буквено-цифрових символів на `-`. Для «Test.allTheThings() T-Shirt (Red)» реальний атрибут — `add-to-cart-test.allthethings()-t-shirt-(red)` (крапка й дужки лишаються), тож метод давав неіснуючий селектор. 14 перших тестів цей товар не торкались, тому помилка сиділа непомітно. Помітив, коли конвеєр-генератор (`claude -p`) для TC-UI-003 («додати всі товари») звернувся до цього товару: агент у своєму звіті вказав на дефект `slug()`.
   _Що виправив:_ підтвердив реальні `data-test` скриптом-пробою на живій сторінці, `slug()` тепер міняє лише пробіли на `-`. Додатково зʼясував: агент-генератор обійшов проблему окремим методом `addAllToCart()` через `getByRole`, а сам `slug()` не чіпав — виправлення моє.

5. **Дрібна помилка форматування в згенерованому коді.** Агент-генератор (TC-UI-004) вніс у `CheckoutPage` рядок `this.error =page.getByTestId('error')` без пробілу. На роботу це не впливає, помітив у `git diff` після прогону. Виправив вручну; висновок — diff після кожної генерації треба читати, а не покладатись лише на зелений тест.
